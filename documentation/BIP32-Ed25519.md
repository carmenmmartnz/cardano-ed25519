# BIP32-Ed25519: Study Notes

> Paper: *Hierarchical Deterministic Keys over a Non-linear Keyspace*
> Authors: Dmitry Khovratovich & Jason Law (Evernym, Inc.)

---

## 0. Why This Paper Exists

**Bitcoin's BIP32** allows generating a whole *tree* of key pairs from a single seed — a "wallet". It works because secp256k1 private keys form a **linear space**: you can derive a child private key by simply adding a number to the parent: $k_{\text{child}} = k_{\text{parent}} + Z_L \pmod{n}$, with equivalent public key $A_{\text{child}} = [k_{\text{child}}]B  = A_{\text{parent}} + [Z_L]B$.

**Ed25519** is different. Its private keys must satisfy strict bit-level constraints (certain bits set/cleared). This means the keyspace is **non-linear** — you can't simply add to a key and stay valid.

This paper shows how to adapt BIP32 for Ed25519 with minimal modifications, keeping compatibility with both standards.

## 1. Background: Ed25519

### 1.1 The Curve

- Prime field $\mathbb{F}_p$ where $p = 2^{255} - 19$
- Base point $B$ of order $n = 2^{252} + 27742317777372353535851937790883648493$
- Identity point: $(0, 1)$
- Infinity point: $(0, 0)$

### 1.2 ED25519 Key Generation

#### Functions used

| Symbol | Input | Output | Name |
|--------|-------|--------|------|
| $H_{512}$ | any byte string | 64 bytes (512 bits) | SHA-512 |

The reason for hashing $\tilde{k}$ rather than using it directly: SHA-512 stretches the 32-byte secret into 64 bytes with uniformly distributed bits, providing both $k_L$ (for signing) and $k_R$ (for nonce generation) from a single secret.

---

Starting from a 32-byte random master secret $\tilde{k}$:

1. Compute $k = H_{512}(\tilde{k})$ — this is the **extended private key** (64 bytes)
2. Split into $k_L$ (left 32 bytes) and $k_R$ (right 32 bytes)
3. **Clamp $k_L$** (mandatory bit constraints):
   - Clear the **3 lowest bits** of byte 0 (index 0)
   - Clear the **highest bit** of byte 31
   - Set the **second highest bit** of byte 31
4. Public key: $A = [k_L]B$ (scalar multiplication of base point)

#### Clamping — bit layout

$k_L$ is 32 bytes. In **little-endian**, byte 0 holds the least significant bits of the scalar and byte 31 holds the most significant bits.

```
k_L (32 bytes, little-endian):

 byte 0                                                        byte 31
┌────────┬────────┬────────┬──────────────────────────────────┬────────┐
│  [0]   │  [1]   │  [2]   │            . . .                 │  [31]  │
│ bits   │ bits   │ bits   │                                  │ bits   │
│  0–7   │  8–15  │ 16–23  │                                  │248–255 │
└────────┴────────┴────────┴──────────────────────────────────┴────────┘
    ↑  least significant bits of the scalar                        ↑
                                               most significant bits of the scalar
```

**Byte 0** (scalar bits 0–7):

```
 bit index
 within byte:   7    6    5    4    3    2    1    0
              ┌────┬────┬────┬────┬────┬────┬────┬────┐
              │ ?  │ ?  │ ?  │ ?  │ ?  │ 0  │ 0  │ 0  │
              └────┴────┴────┴────┴────┴────┴────┴────┘
                                         ↑    ↑    ↑
                                       clear clear clear
                                    (bits 2,1,0 → k_L divisible by 8)
```

**Byte 31** (scalar bits 248–255):

```
 bit index
 within byte:   7    6    5    4    3    2    1    0
              ┌────┬────┬────┬────┬────┬────┬────┬────┐
              │ 0  │ 1  │ ?  │ ?  │ ?  │ ?  │ ?  │ ?  │
              └────┴────┴────┴────┴────┴────┴────┴────┘
                ↑    ↑
              clear  set
            (bit 255) (bit 254)
         → guarantees 2^254 ≤ k_L < 2^255
```

**Why each operation:**

- **Clear bits 0–2 of byte 0** — small-order subgroup attack.

  **The attack setup**

  The Ed25519 curve has a cofactor of 8, meaning it contains points of order 1, 2, 4, and 8 in addition to the main $n$-order subgroup. Call $P$ a point of order 8, meaning:

  $$[8]P = O \quad \text{(identity)}$$

  Therefore $[k]P$ repeats with period 8 — it depends only on $k \bmod 8$:

  | $k \bmod 8$ | $[k]P$ |
  |---|---|
  | 0 | $O$ |
  | 1 | $P$ |
  | 2 | $2P$ |
  | 3 | $3P$ |
  | 4 | $4P$ |
  | 5 | $5P$ |
  | 6 | $6P$ |
  | 7 | $7P$ |

  There are only 8 possible outcomes. This follows from the distributive property of scalar multiplication and the fact that $[8]P = O$:

  $$[k]P = [q \cdot 8 + r]P = \underbrace{q \cdot [8]P}_{q \cdot O\ =\ O} + [r]P = [r]P = [k \bmod 8]\ P$$

  **The attack**

  In a key agreement protocol (like Diffie-Hellman), the attacker sends $P$ (a small-order point) instead of a legitimate public key. The victim computes $[k_L]P$ and uses it as a shared secret to encrypt a response. The attacker tries all 8 possible values $\{O, P, 2P, \ldots, 7P\}$ as decryption keys — one will work, immediately revealing $k_L \bmod 8$ — the 3 lowest bits of the private key.

  Repeat with different small-order points across multiple sessions and more bits leak.

  **The fix**

  By clearing bits 0–2, $k_L$ is always divisible by 8, so $k_L \bmod 8 = 0$ always. Then $[k_L]P = [0]P = O$ for any small-order point $P$, regardless of what $k_L$ actually is. The result is always the identity — nothing is revealed.

- **Clear bit 7 of byte 31 (bit 255)** — ensures $k_L < 2^{255}$, keeping the scalar within the valid field range.

- **Set bit 6 of byte 31 (bit 254)** — prevents timing side-channel attacks via the double-and-add algorithm used for scalar multiplication $[k_L]B$:

  ```
  result = identity point
  for each bit of k, from the HIGHEST SET BIT down to bit 0:
      result = result + result   (double)
      if this bit is 1:
          result = result + B    (add)
  return result
  ```

  The number of iterations equals the position of the highest set bit. If that position varies between keys, the time taken varies too — an attacker measuring execution time learns the approximate magnitude of $k_L$.

  | $k_L$ highest set bit | Iterations |
  |---|---|
  | bit 252 | 253 |
  | bit 253 | 254 |
  | bit 254 | 255 |

  By forcing bit 254 = `1` and bit 255 = `0`, every valid $k_L$ has the same binary length:

  ```
  bit: 255  254  253  252  ...  0
         0    1    ?    ?  ...  ?
  ```

  The highest set bit is **always at position 254**, so the algorithm always runs for exactly 255 iterations regardless of the other bits. No timing variation → no information leaked.

  **Example — computing $[13]B$:**

  $13$ in binary is `1101`, highest set bit at position 3.

  | Step | Bit | Operation | Result |
  |------|-----|-----------|--------|
  | start | — | — | $O$ (identity) |
  | bit 3 = `1` | double | $O + O = O$ | $O$ |
  | | add $B$ | $O + B$ | $B$ |
  | bit 2 = `1` | double | $B + B$ | $2B$ |
  | | add $B$ | $2B + B$ | $3B$ |
  | bit 1 = `0` | double | $3B + 3B$ | $6B$ |
  | | *(skip)* | bit is 0, no add | $6B$ |
  | bit 0 = `1` | double | $6B + 6B$ | $12B$ |
  | | add $B$ | $12B + B$ | $13B$ |

  The loop ran **4 iterations** because the highest bit was at position 3. If $k$ were $5$ = `101` (highest bit at position 2), it would run only **3 iterations** — and that difference in timing is observable from the outside.

## 2. Background: BIP32

BIP32 creates a **key tree** from a single seed. Each node has:
- A private/public key pair
- A **chain code** (shared secret for deriving children)
- A **child index** (0 to $2^{32} - 1$)

### Key properties:
- Indices $i < 2^{31}$: **normal** children — public key derivable by anyone with the chain code
- Indices $i \geq 2^{31}$: **hardened** children — requires parent private key; more secure, but breaks public-only derivation

### Why BIP32 doesn't work for Ed25519 directly:

In BIP32, $k_{\text{child}} = k_{\text{parent}} + Z_L \bmod n$. The result is a valid scalar for secp256k1. But for Ed25519, adding anything to $k_L$ breaks the clamping constraints — the resulting value may not pass the bit requirements.

---

## 3. BIP32-Ed25519: The Adaptation

### Core idea

Instead of working with the 32-byte raw secret $\tilde{k}$, work with the **64-byte extended private key** $k = (k_L, k_R)$ throughout. The key derivation operates on these extended keys while preserving the bit constraints.

### 3.1 Root Key Generation

Given a 256-bit master secret $\tilde{k}$:

1. Compute $k = H_{512}(\tilde{k})$; split into $k_L \| k_R$
2. **If the third-highest bit of $k_L[31]$ is set → discard and retry with a new $\tilde{k}$**
3. Apply clamping to $k_L$ as in standard Ed25519
4. Root public key: $A = [k_L]B$
5. Root chain code: $c \leftarrow H_{256}(\texttt{0x01} \| \tilde{k})$ (SHA-256)

**Why discard in step 2?**

The clamping constraint requires bit 255 of $k_L$ to stay `0` at every level of the tree — not just the root. The problem is that each child derivation **adds** to $k_L$:

$$k_L^{\text{child}} = 8 \cdot Z_L + k_L^{\text{parent}}$$

where each addition is at most $2^{227}$, and the tree goes up to $2^{20}$ levels deep. The total accumulated addition across the whole tree is at most:

$$2^{20} \times 2^{227} = 2^{247}$$

Think of it like a counter with a hard ceiling of $2^{255}$. If the root starts too close to the ceiling, the additions will eventually push past it and break the constraint.

- **Bit 253 set** → root $k_L \geq 2^{254} + 2^{253}$ → adding $2^{247}$ can push past $2^{255}$ → **unsafe**
- **Bit 253 cleared** → root $k_L < 2^{254} + 2^{253}$ → adding $2^{247}$ stays below $2^{255}$ → **always safe**

Discarding $\tilde{k}$ when bit 253 is set is simply rejecting starting values that are too close to the ceiling.

### 3.1.1 Cardano Icarus Variant

The paper's section 3.1 derives the root key from a raw 256-bit secret $\tilde{k}$. Cardano's **Icarus** scheme (CIP-0003) targets BIP39 mnemonics directly and makes two structural changes: it replaces SHA-512 with PBKDF2, and it forces bit 253 to zero instead of retrying.

#### Functions used

| Symbol | Input | Output | Name |
|--------|-------|--------|------|
| $\text{PBKDF2}$ | passphrase, entropy, iterations, dkLen | 96 bytes | PBKDF2-HMAC-SHA512 |

#### Steps

Given BIP39 entropy bytes $e$ (16–32 bytes) and an optional passphrase $p$:

1. Compute 96 bytes: $\text{raw} \leftarrow \text{PBKDF2-HMAC-SHA512}(\text{password}=p,\ \text{salt}=e,\ \text{iterations}=4096,\ \text{dkLen}=96)$
2. Split: $k_L = \text{raw}[0:32]$, $k_R = \text{raw}[32:64]$, $c = \text{raw}[64:96]$
3. **Clamp $k_L$:**
   - `kL[0]  &= 0xF8` — clear bits 0, 1, 2
   - `kL[31] &= 0x1F` — clear bits 5, 6, 7
   - `kL[31] |= 0x40` — set bit 6
4. Root public key: $A = [k_L]B$

#### Bit state of $k_L[31]$ after clamping

```
 bit within byte 31:   7    6    5    4    3    2    1    0
                     ┌────┬────┬────┬────┬────┬────┬────┬────┐
                     │ 0  │ 1  │ 0  │ ?  │ ?  │ ?  │ ?  │ ?  │
                     └────┴────┴────┴────┴────┴────┴────┴────┘
                       ↑    ↑    ↑
                     clear  set  clear   ← forced, not tested
                    (255) (254) (253)
```

The critical difference from section 3.1: **bit 253 is always forced to 0** by the `& 0x1F` mask. The paper rejects and retries if this bit is set; Icarus simply clears it. The tree-safety guarantee is the same — bit 253 of every root $k_L$ is 0 — but Icarus achieves it deterministically with no retry.

#### Differences from the paper (section 3.1)

| | Paper | Icarus |
|---|---|---|
| Input | 256-bit secret $\tilde{k}$ | BIP39 entropy + passphrase |
| Key stretch | $H_{512}(\tilde{k})$ (SHA-512, one pass) | PBKDF2-HMAC-SHA512, 4096 iterations |
| Chain code | $H_{256}(\texttt{0x01} \| \tilde{k})$ (separate SHA-256 call) | $\text{raw}[64:96]$ (directly from PBKDF2 output) |
| Bit 253 constraint | Reject $\tilde{k}$ if set, retry with a new one | Force to 0 via `& 0x1F` mask |
| Retry possible | Yes | No — always deterministic |

The PBKDF2 iteration count (4096) provides brute-force resistance against attackers who try to enumerate mnemonics: each guess requires 4096 SHA-512 calls rather than one.

### 3.2 Child Private Key Derivation

Let $(k^P, c^P, A^P)$ be the parent's (extended private key, chain code, public key). These come from whichever node is the parent in the tree:

- **First derivation (root → child):** $(k^P, c^P, A^P)$ are the outputs of section 3.1 steps 1–5
- **Deeper levels (child → grandchild):** $(k^P, c^P, A^P)$ are the $k_L^i, k_R^i, c_i, A_i$ computed in the previous derivation — each node's outputs become the next node's inputs

$F_K$ denotes **HMAC-SHA512** with key $K$ — a construction that runs SHA-512 with a secret key to produce a 64-byte output. Here the key is always the parent chain code $c^P$, which is why you see $F_{c^P}(\ldots)$ throughout.

**Step 1 — Compute $Z$ (512-bit value, split into $Z_L \| Z_R$):**

$$
Z \leftarrow \begin{cases}
F_{c^P}(\texttt{0x02} \| A^P \| i) & i < 2^{31} \\
F_{c^P}(\texttt{0x00} \| k^P \| i) & i \geq 2^{31}
\end{cases}
$$

Where:
- $A^P$ is serialized as little-endian 32-byte string
- $k^P = (k_L^P, k_R^P)$ both serialized as little-endian
- $i$ is serialized as little-endian 4-byte string
- $Z_L$ = left **28 bytes** of $Z$ (not 32!) — **crucial difference**
- $Z_R$ = right 32 bytes of $Z$

**Step 2 — Derive child extended private key:**

$$
k_L^i \leftarrow 8 \cdot [Z_L] + [k_L^P]
$$
$$
k_R^i \leftarrow ([Z_R] + [k_R^P]) \bmod 2^{256}
$$

If $k_L^i$ is divisible by the base order $n$ → discard this child index.

**Step 3 — Child chain code:**

$$
c_i \leftarrow \begin{cases}
\text{right}_{32}\!\left(F_{c^P}(\texttt{0x03} \| A^P \| i)\right) & i < 2^{31} \\
\text{right}_{32}\!\left(F_{c^P}(\texttt{0x01} \| k^P \| i)\right) & i \geq 2^{31}
\end{cases}
$$

**Recap:**

| Prefix | Context | What it computes |
|--------|---------|-----------------|
| `0x00` | Hardened $i$ | $Z$ for private child key derivation |
| `0x01` | Hardened $i$ | Chain code for hardened child |
| `0x02` | Normal $i$ | $Z$ for public/private child key derivation |
| `0x03` | Normal $i$ | Chain code for normal child |

### 3.3 Child Public Key Derivation

Can be done **without the private key** for non-hardened children only.

**Step 1 — Compute $Z$** (same as non-hardened private case):

$$
Z \leftarrow F_{c^P}(\texttt{0x02} \| A^P \| i)
$$

**Step 2 — Derive child public key:**

$$
A_i \leftarrow A^P + [8 \cdot Z_L]B
$$

Where $Z_L$ is the left 28 bytes of $Z$ interpreted as a **224-bit little-endian integer**.

If $A_i$ is the identity point $(0, 1)$ → discard this child index.

**Step 3 — Child chain code** (same as in private derivation).

> The factor of $8$ in $8 \cdot Z_L$ is the key insight. It ensures the third-highest bit constraint is maintained across derivation levels.

## 4. The Six Modifications from BIP32

| # | Modification | Reason |
|---|---|---|
| 1 | Work with 64-byte extended key $k$ instead of 32-byte $\tilde{k}$ | Ed25519 keys need the extra 32 bytes ($k_R$) for nonce generation |
| 2 | Reject master secrets where 3rd-highest bit of $k_L[31]$ is set | Guarantees child $k_L$ will always have 2nd-highest bit = 1 |
| 3 | Extra HMAC call to accommodate the longer private key | HMAC-SHA512 produces only 64 bytes; key is 64 bytes |
| 4 | $Z_L$ truncated to **28 bytes** (not 32) | Ensures $8 \cdot Z_L + k_L^P$ keeps the second-highest bit set |
| 5 | Maximum tree depth: $2^{20} = 1{,}048{,}576$ levels | Prevents overflow of the bit constraints across many derivations |
| 6 | All integers in **little-endian** format | Consistent with Ed25519 and EdDSA conventions |

## 5. Security Analysis

### Master Key

- The 512-bit extended key has 6 bits fixed → effectively 506 bits of entropy
- An attacker would need $2^{506}$ attempts to brute-force the extended key directly
- But they'd more naturally try $2^{256}$ different master secrets $\tilde{k}$
- Either way: **no security loss**

### Child Key Collisions

- There are $2^{224}$ distinct values for $Z_L$ (28 bytes)
- Collisions in $k_L$ are possible for $\approx 2^{112}$ keys
- However: $k_R$ is independent of $k_L$, so collisions don't enable signature forgery
- **No overall security degradation**

### Bit Constraint Proof

All produced values $a$ (the scalar in $k_L$) satisfy Ed25519 requirements:

- Root: $a = 2^{254} + 8b$ where $b < 2^{250}$ (by construction)
- Child at level $j$: $a^j = a + \sum_{j' < j} 8M_L^{j'}$ where each $M_L < 2^{224}$
- Since $j \leq 2^{20}$, we get $a^j \leq 2^{254} + 2^{253} + 2^{247}$ → constraints satisfied ✓

## 6. The Key Tree

```
                    root (k̃)
                   /    |    \
              child_0  ...  child_(2^32-1)
             /    \
       grandchild_0  ...
```

- Any node with $i < 2^{31}$ can parent further children
- A path $m \to i_1 \to i_2 \to \ldots \to i_l$ uniquely identifies a key at depth $l$
- Max depth: $2^{20}$
- **Normal children** ($i < 2^{31}$): public key derivable without parent private key
- **Hardened children** ($i \geq 2^{31}$): derivation requires parent private key; compromise of a child doesn't endanger the parent

## 8. BIP44 Path Derivation — Worked Example

BIP44 is a convention that defines a specific structure for the derivation path:

```
m / purpose' / coin_type' / account' / role / address_index
```

For Cardano Shelley: `m / 1852' / 1815' / 0' / 0 / 0`

A `bip44_path_t` stores this as an array of `uint32` values, with hardened indices having bit $2^{31}$ set:

```c
path = { 0x8000073C, 0x80000717, 0x80000000, 0, 0 }
//        1852'        1815'        0'          0  0
```

The derivation applies section 3.2 five times in sequence — each level's output feeds into the next as the parent.

---

**Start: root** (from section 3.1)

$$\tilde{k} \xrightarrow{H_{512}} (k_L, k_R) \xrightarrow{\text{clamp}} A = [k_L]B, \quad c = H_{256}(\texttt{0x01} \| \tilde{k})$$

---

**Level 1 — index 1852' (hardened, $i = 1852 + 2^{31}$)**

Since $i \geq 2^{31}$ → uses **private key** branch:

$$Z \leftarrow F_{c^{\text{root}}}(\texttt{0x00} \| k^{\text{root}} \| i)$$
$$k_L^1 = 8 \cdot Z_L + k_L^{\text{root}}, \quad k_R^1 = (Z_R + k_R^{\text{root}}) \bmod 2^{256}$$
$$A^1 = [k_L^1]B, \quad c^1 = \text{right}_{32}(F_{c^{\text{root}}}(\texttt{0x01} \| k^{\text{root}} \| i))$$

---

**Level 2 — index 1815' (hardened, $i = 1815 + 2^{31}$)**

Since $i \geq 2^{31}$ → uses **private key** branch:

$$Z \leftarrow F_{c^1}(\texttt{0x00} \| k^1 \| i)$$
$$k_L^2 = 8 \cdot Z_L + k_L^1, \quad k_R^2 = (Z_R + k_R^1) \bmod 2^{256}$$
$$A^2 = [k_L^2]B, \quad c^2 = \text{right}_{32}(F_{c^1}(\texttt{0x01} \| k^1 \| i))$$

---

**Level 3 — index 0' (hardened, $i = 0 + 2^{31}$)**

Since $i \geq 2^{31}$ → uses **private key** branch:

$$Z \leftarrow F_{c^2}(\texttt{0x00} \| k^2 \| i)$$
$$k_L^3 = 8 \cdot Z_L + k_L^2, \quad k_R^3 = (Z_R + k_R^2) \bmod 2^{256}$$
$$A^3 = [k_L^3]B, \quad c^3 = \text{right}_{32}(F_{c^2}(\texttt{0x01} \| k^2 \| i))$$

---

**Level 4 — index 0 (non-hardened, $i = 0$)**

Since $i < 2^{31}$ → uses **public key** branch (no private key needed):

$$Z \leftarrow F_{c^3}(\texttt{0x02} \| A^3 \| i)$$
$$k_L^4 = 8 \cdot Z_L + k_L^3, \quad k_R^4 = (Z_R + k_R^3) \bmod 2^{256}$$
$$A^4 = A^3 + [8 \cdot Z_L]B, \quad c^4 = \text{right}_{32}(F_{c^3}(\texttt{0x03} \| A^3 \| i))$$

---

**Level 5 — index 0 (non-hardened, $i = 0$)**

Since $i < 2^{31}$ → uses **public key** branch:

$$Z \leftarrow F_{c^4}(\texttt{0x02} \| A^4 \| i)$$
$$k_L^5 = 8 \cdot Z_L + k_L^4, \quad k_R^5 = (Z_R + k_R^4) \bmod 2^{256}$$
$$A^5 = A^4 + [8 \cdot Z_L]B, \quad c^5 = \text{right}_{32}(F_{c^4}(\texttt{0x03} \| A^4 \| i))$$

---

**Final key at `m/1852'/1815'/0'/0/0`:**

| | Value |
|---|---|
| Private key | $(k_L^5,\ k_R^5)$ |
| Public key | $A^5$ |
| Chain code | $c^5$ |

The first 3 levels are hardened — an attacker who learns $A^5$ cannot work backwards to the account-level keys. The last 2 levels are non-hardened — $A^5$ could be derived from $A^3$ alone without ever touching the private key.

| Index | Name | Cardano value | Always hardened? |

### ED25519 Signature for Message $M$

#### Notation and definitions

**$\|$** denotes byte string concatenation — the inputs are joined end to end before hashing:

$$H_{512}(k_R \| M) = H_{512}(\underbrace{k_R}_{\text{32 bytes}} \underbrace{M}_{\text{any length}})$$

**Encoding of a point** — a curve point has two coordinates $(x, y)$. Ed25519 compresses them into 32 bytes:
1. Take the $y$ coordinate (32 bytes, little-endian)
2. Copy the least significant bit of $x$ into the most significant bit of byte 31

The $x$ coordinate can be recovered from $y$ using the curve equation (it has two solutions; the saved bit picks the right one).

**$A$** is the signer's public key: $A = [k_L]B$ (from step 4 of section 1.2). It is included in the hash for $x$ to bind the signature to a specific key pair — preventing an attacker from claiming the same $(R, S)$ was produced by a different key.

#### Variables

| Variable | Role |
|---|---|
| $r$ | Secret nonce — used once, never revealed |
| $R = [r]B$ | Public commitment to the nonce (a curve point, encoded to 32 bytes) |
| $x$ | Challenge — hash of $R$, $A$, $M$ so neither party controls it |
| $S$ | Response — combines nonce and private key |

#### Steps

1. $r \leftarrow H_{512}(k_R \| M) \bmod n$
2. Compute point $[r]B$, let $R$ be its 32-byte encoding
3. $x \leftarrow H_{512}(R \| A \| M)$ interpreted as 64-byte integer
4. $S = (r + x \cdot k_L) \bmod n$
5. Signature $= R \| S$

#### Why $k_R$ generates $r$

$r$ is a nonce. It must be:
- **Secret** — if an attacker knows $r$, they solve $S = r + x \cdot k_L$ directly for $k_L$
- **Unique per message** — reusing $r$ for two messages gives two equations, enough to solve for $k_L$
- **Deterministic** — avoids relying on a random number generator (bad randomness has broken real systems)

$r \leftarrow H_{512}(k_R \| M) \bmod n$ satisfies all three: $k_R$ is secret, $M$ makes it unique per message, and hashing is deterministic.

#### Why a verifier trusts the signature

The verifier recomputes $x = H_{512}(R \| A \| M)$ and checks:

$$[S]B \stackrel{?}{=} R + [x]A$$

This holds because:

$$[S]B = [r + x \cdot k_L]B = \underbrace{[r]B}_{R} + x \cdot \underbrace{[k_L]B}_{A} = R + [x]A$$

The verifier never sees $k_L$ or $r$ — only $R$, $S$, $A$, and $M$. The equation holds only if the signer actually knew $k_L$.

| **Extended private key** | 64-byte key $(k_L, k_R)$ derived from 32-byte secret via SHA-512 |
| **Chain code** | 32-byte shared secret used as HMAC key during child derivation |
| **Hardened child** | Child with index $\geq 2^{31}$; requires parent private key to derive |
| **Normal child** | Child with index $< 2^{31}$; public key derivable from parent public key |
| **Clamping** | Bit manipulation of $k_L$ to ensure valid Ed25519 scalar |
| **$F_K$** | HMAC-SHA512 with key $K$ |
| **Little-endian** | Least significant byte first (used throughout this spec) |
